# Avaliação FBS — HMI Multimodal MUM-T / ISR

## R01 — Input Autopilot Parameters
Conformidade: **Sim.** Touch (keypad na tela, tap em campo) e Keyboard (UCP alfanumérico, rotary encoder, bezel OSS). O rotary encoder e bezel OSS entram legitimamente em Keyboard ("teclado físico e botões"). WAD como superfície de tela (Screen) é subproduto legítimo dos requisitos de input Touch. Nada fora do vocabulário.
Separação de camadas: **Sim.** A Function fala de "supply the numeric flight targets... measurable effect = valid, complete parameter set delivered" — é efeito mensurável, não fluxo. Behaviour descreve o fluxo (selecionar campo → entrar valor → validar → confirmar) sem listar hardware. Structure é concreta (painel WAD com campos ALT/HDG/SPD, keypad, bezel, encoder, gate de validação).
Completude: **Sim.** Dá pra desenhar a tela: três campos com valor atual + range + flag de inválido, keypad invocado no tap, CONFIRM bloqueado até tudo válido.
Nota: **5/5**
Observações: Requisito modelo. Define o gate de validação e o painel que viram base de reuso pra R03/R05/R11. A única imprecisão é o "WAD echo" repetido, mas não compromete.

## R02 — Notify Autopilot Reached
Conformidade: **Sim.** Screen (notification strip, panel cue, texto) + Audio-out (ping, TTS opcional). Conforme.
Separação de camadas: **Sim.** Function separa bem F-02.1 (confirmação de mudança de estado) de F-02.2 (redirecionamento de atenção) sem descrever ordem. Behaviour descreve o disparo simultâneo dos canais. Structure lista os três componentes concretos e já marca a strip como "reusable notification channel".
Completude: **Sim.** Texto específico ('AUTOPILOT TARGET REACHED — [params]'), persistência até superseded/ack, tom distinto de caution/warning.
Nota: **5/5**
Observações: Bem pensado ao estabelecer o canal de notificação reutilizável. Fallbacks Screen-only/Audio-only cobrem a regra de redundância corretamente.

## R03 — Select Autopilot Mode
Conformidade: **Sim.** Touch (tap) + Keyboard (bezel OSS). Conforme.
Separação de camadas: **Parcial.** Function OK (arm + engage como funções acopladas). Mas Behaviour e Structure vazam preocupação de design que enfraquece o requisito: "the cross-modality flow is provided mainly as quality-of-life rather than as a hard guard" e "No enforced modality-switch". Isso é justificativa/racional, não descrição do que o artefato faz. A Structure ("reusing R02 notification-strip logic (armed-state cue)") é aceitável como reuso.
Completude: **Sim.** Dual-addressable AP MODE, primeira atuação = ARM com highlight persistente, segunda = ENGAGE. Desenhável.
Nota: **4/5**
Observações: O padrão arm→engage é sólido, mas o texto gasta espaço justificando por que o cross-modal é "só conforto" — isso deveria ser decisão de Behaviour, não comentário meta. Estado armado persistir no painel (não no canal de input) é bem colocado.

## R04 — Stop Using Autopilot
Conformidade: **Sim.** Touch + Keyboard (bezel OSS). Conforme.
Separação de camadas: **Sim.** Function limpa (relinquish authority, deliberate command). Behaviour descreve press-and-confirm cross-modal. Structure é honesta ao declarar "Only deltas from R03 are label/state text and confirm prompt wording."
Completude: **Parcial.** É consistente e reusa R03 corretamente, mas a substância própria é mínima — quase todo o conteúdo é "igual a R03 com outro rótulo". Aceitável para um toggle inverso, mas não tem substância independente suficiente pra ser 5.
Nota: **4/5**
Observações: Reuso correto e econômico. A dependência total de R03 é apropriada aqui, não é preguiça.

## R05 — Report Intelligence Data
Conformidade: **Sim.** Touch + Keyboard. Conforme.
Separação de camadas: **Sim.** Function distingue bem conteúdo autorado pelo piloto vs. metadata auto-anexada (read-only envelope) — boa delimitação de escopo. Behaviour descreve entrada interleaved + gate. Structure lista campos concretos (event type, classification, coordinates, free-text) e o dual-confirm.
Completude: **Sim.** Campos nomeados, tipos de campo (categorical cycle vs free-text), auto-append de alt/pos/timestamp. Desenhável.
Nota: **5/5**
Observações: Forte. Já sinaliza reuso pro R07 (surveillance). O "dual-confirm send via Touch OSS AND bezel OSS (both live)" é levemente ambíguo — "both live" significa qualquer um confirma, não os dois obrigatórios; o texto poderia ser mais preciso.

## R06 — Communicate Order
Conformidade: **Sim.** Screen (strip, lista, HUD summary, detalhe) + Audio-out (ping). Conforme.
Separação de camadas: **Parcial.** Function subdivide em alerta/apresentação/persistência de forma clara. Porém há vazamento: Be-06.3.1 menciona "opened via out-of-scope input" e F-06.2 diz "satisfied by the system storing and ordering received notifications" — a Function está descrevendo o mecanismo de solução ("satisfied by...") em vez de só o propósito. Structure é concreta e boa (list/detail compartilhando um order store).
Completude: **Sim.** Rows = timestamp + title, ordenação por chegada/prioridade, HUD count line, detail view compartilhando dados.
Nota: **4/5**
Observações: A tríade função é bem decomposta, mas cada Function carrega um "satisfied by..." que é conteúdo de Structure/Behaviour empurrado pra camada errada.

## R07 — Report Surveillance Event
Conformidade: **Sim.** Touch + Keyboard. Conforme.
Separação de camadas: **Sim.** Function distingue nitidamente de R05: "what is new here is the trigger side, not the transmission" — excelente delimitação. Behaviour descreve gestão per-step de triggers + dispatch automático não-atendido. Structure concreta (trigger-list + editor, arm-gate como único gate, monitoramento interno).
Completude: **Sim.** Rows = title + condition summary + armed indicator, campos, arm press-and-confirm, dispatch instantâneo com notificação post-send. Desenhável.
Nota: **5/5**
Observações: Muito bom. A distinção entre "instant unattended transmit" e "notification output-only, not a confirmation gate" é precisa e evita confundir alerta com gate. Reuso bem mapeado (R01 gate, R05 transmit plumbing sem a UI de confirm, R02/R06 alert).

## R08 — Communicate Message (system→user)
Conformidade: **Sim.** Screen (strip tiered, HUD banner) + Audio-out (ping/tone/TTS). Conforme.
Separação de camadas: **Sim.** Function foca em triagem por prioridade (efeito: alocação de atenção). Behaviour mapeia routine/elevated/critical a número de canais — o "channel-count as priority cue" é bom design de Behaviour. Structure concreta (três tiers visuais, message store, mirror HUD, mapeamento de áudio por tier, único Acknowledge).
Completude: **Sim.** Tempos (auto-dismiss ~5s), comportamento por tier, ack sincronizado WAD+HUD+audio. Altamente desenhável.
Nota: **5/5**
Observações: Cronologicamente fechado depois de R02/R06 mas declarado como "foundational... reused by R02, R06". Há uma leve inversão de dependência (R02/R06 já referenciavam a strip antes de R08 formalizá-la), mas o resultado é consistente. Requisito modelo.

## R13 — Communicate UAV Status
Conformidade: **Sim.** Screen + Audio-out. Conforme.
Separação de camadas: **Sim.** Function foca em sinalizar deltas (event-driven), complementando R12 (values-on-demand). Behaviour: cue sincronizado graded por criticidade. Structure introduz um único component novo (change-detector no store de R12) e reusa R08 + R12 — arquitetura limpa.

## R14 — Input Sensor Move
Conformidade: **Parcial.** Touch OK. HMD OK. Mas Be-14.2 é explicitamente declarado "HMD-assisted, not HMD-alone-complete (accepted deviation)" — ou seja, o pathway HMD não completa a tarefa sozinho (commit via bezel OSS ou WAD tap, que é Keyboard/Touch, não HMD). Como bezel OSS não está entre as modalidades fixas de R14 (só Wearable/HMD e Touch), o commit por OSS é uma leve violação além do desvio já admitido. O tap WAD salva parcialmente.
Separação de camadas: **Sim.** Function (designar aim-point, converter POI/AOI em slew-and-hold; steering contínuo deferido). Behaviour descreve os três pathways. Structure concreta (tap-to-drop/drag-box, reticle head-slaved + eye-tracked offset).
Completude: **Sim.** Marker, drag-box AOI, reticle in-visor, slew-progress. Desenhável.
Nota: **3/5**
Observações: O desvio HMD é honestamente declarado, o que é bom, mas ainda assim é o único requisito onde uma modalidade fixa não completa a tarefa sozinha, e o commit via bezel OSS introduz uma modalidade não-listada. Baixa a nota. Deferir steering contínuo é decisão de escopo legítima.

## Resumo geral

**Cobertura: 20/20 requisitos fechados** (nenhum faltando). Todos os 20 requisitos da lista têm Function, Behaviour e Structure preenchidos.

**Consistência:** Alta e deliberada. Os pares espelhados são tratados de forma coerente:
- R01↔R11 (ownship vs UAV params) — mesmo padrão, clone-with-own-state.
- R09/R10 (takeover request/command) ↔ R19/R20 (handover request/command) — inversos simétricos.
- R12 (values-on-demand) vs R13 (change-signal) — separação limpa mantida.
- O gate dual-input press-and-confirm é o mesmo em R03/R04/R05/R09/R10/R17/R19/R20 — critério único aplicado consistentemente.
Contradição de critério mínima. A única assimetria de qualidade notável: R19 é bem mais raso que seu análogo R09, quebrando levemente a expectativa de tratamento simétrico entre pares.

**Padrões recorrentes:**
- *Bom:* framework de notificação (strip + audio + HUD) estabelecido cedo (R02) e formalizado em R08, reusado consistentemente por R06/R07/R10/R13/R17/R20. Economia arquitetural real, não citação vaga.
- *Bom:* clone-with-own-state (R11→R12→R16) declarado explicitamente cada vez, com estado independente e co-display. Rastreável.
- *Bom:* gate único de validação reaproveitado com semântica consistente.
- *Problemático menor:* referências a códigos/UCs externos não presentes na lista ("R4.2.2", "step 5.2.7", "UC 7.2.2–7.2.4", "UC8.1.16", "8-layer stacking logic") aparecem sem definição — ruído de rastreabilidade, não afeta a desenhabilidade mas prejudica auto-suficiência do documento.
- *Problemático recorrente leve:* algumas Functions carregam "satisfied by..." (R06) ou racional de design (R03), empurrando conteúdo de Behaviour/Structure pra camada de Function.
- *Único desvio de conformidade real:* R14, onde o pathway HMD não é auto-completo e o commit via bezel OSS toca uma modalidade fora das fixas do requisito. Honestamente declarado, mas é o ponto fraco de conformidade do conjunto.

**Nota geral do conjunto: 5/5**

Conjunto forte e coerente. Cobertura total, reuso arquitetural disciplinado e rastreável, separação de camadas geralmente limpa, e vários requisitos (R01, R02, R07, R08, R13, R18) são modelos do que se espera. Os defeitos são localizados e menores: o desvio de conformidade em R14, a rasura relativa de R19, e o ruído de referências a UCs externos indefinidos. Nenhum requisito precisa refazer; o pior (R14, R19) fica em "aceitável/usável". A consistência entre pares espelhados e a construção incremental de frameworks compartilhados elevam o conjunto acima da soma dos requisitos individuais.
